# 《架构演进与运维方案》审查报告

> 审查日期：2026-08-10  
> 审查范围：`docs/架构演进与运维方案.md` v0.11、当前仓库中的 Compose、启动代码、迁移脚本、备份脚本和 LiteLLM 集成。  
> 审查方式：静态对照；未连接生产服务器，未执行生产变更。

## 1. 结论摘要

方案方向是合理的：将 API/Query、Scheduler、Collector 和数据库职责分离，以 MySQL 作为事实状态源，用租约、`lease_token`、`lease_generation`、Outbox 和可验证备份支撑“计算可抛弃”。当前仓库已经落地了部分 Phase A 基础能力，例如独立 Scheduler/Collector 入口、`FOR UPDATE SKIP LOCKED` 任务领取、GTID/binlog 配置和增强版备份脚本。

但“文档目标架构”和“可直接用于多节点生产的实现”之间仍有明显差距。当前不建议直接按文档进入多节点扩容或数据库拆分，优先修复以下三个阻断项：

1. API 进程仍会在启动时执行 `create_all`/列级迁移；如果以后横向启动多个 API，会产生启动竞态和职责越界。
2. LiteLLM 动态配置存在容器路径不一致：后端写 `/app/litellm_config.yaml`，LiteLLM 读取 `/app/config.yaml`，动态修改很可能不会生效。
3. `backup_db.sh --verify-restore` 的多库恢复校验逻辑有问题，且 `deploy_prod.sh` 仍按单库变量回滚；在正式拆分三库前必须先修正并完成隔离恢复演练。

因此当前状态应标记为：**单机可运行、Phase A 部分实现、尚未达到文档描述的可扩展生产基线**。

## 2. 分级结论

| 等级 | 结论 | 影响 |
|---|---|---|
| P0 | API 启动职责未完全拆出 | 多副本部署时可能重复迁移、重复初始化或重复调度 |
| P0 | LiteLLM 配置写入和读取路径不一致 | 管理页面更新模型后，网关可能继续使用旧配置 |
| P0 | 多库备份恢复校验与回滚仍不闭环 | 备份“成功”不等于能恢复，升级失败时可能无法可靠回滚 |
| P1 | Compose 仍是单机绑定配置 | 固定容器名、`build`、`mysql` 服务名和 Docker Socket 阻碍 N 节点部署 |
| P1 | 进度状态仍是进程内存 | API 重启或多副本后进度不可见、不一致 |
| P1 | 文档部分“当前状态”已过时 | 实施人员会按旧判断重复改造或漏掉已完成工作 |
| P2 | 副本、对象存储、Tailscale/DNS、K3s 尚未验证 | 容灾和跨节点能力仍停留在设计/条件阶段 |

## 3. 已实现和部分实现的内容

### 3.1 已有较好基础

- 独立 Scheduler 和 Collector 命令入口已存在，Collector 使用 `FOR UPDATE SKIP LOCKED` 领取任务，并通过应用生成的 UUID 作为 `lease_token`。
- `collection_tasks`、`control_outbox`、`scheduler_leader_lease` 等 Phase A 表的迁移脚本已经存在，具备继续完善幂等迁移的基础。
- `deploy/config/mysql.cnf` 已开启 ROW binlog、`sync_binlog=1`、GTID 和 `innodb_flush_log_at_trx_commit=1`，方向与 PITR/复制设计一致。
- `scripts/backup_db.sh` 已支持目标数据库列表、`--source-data=2`、SHA-256 元数据和可选恢复校验。文档中“脚本尚未升级”的描述已经落后于代码。
- `scripts/deploy_prod.sh` 已具备升级前备份、显式迁移、用户/表数量检查、健康检查和回滚框架。

### 3.2 仍属于“过渡实现”

- API 默认不启动 Scheduler，但代码仍保留 `API_START_SCHEDULER=true` 兼容开关；API lifespan 仍无条件调用 `init_db()`。
- Compose 已声明独立 Scheduler/Collector 服务，但它们仍然从源码 `build`，并且所有服务都连接同一个 Compose 内的 `mysql` 服务。
- 任务租约已经具备 fencing 结构，但同步进度仍由进程内全局对象保存，尚未形成跨副本的持久化查询模型。

## 4. 重点问题与修复建议

### P0-1：API 仍承担数据库初始化/迁移职责

证据：[`backend/app/main.py`](../backend/app/main.py:71) 定义 `init_db()`，其中调用 `Base.metadata.create_all`；[`backend/app/main.py`](../backend/app/main.py:428) 在 lifespan 启动时无条件调用；同一文件还保留列级迁移调用。Scheduler 虽通过 `API_START_SCHEDULER` 默认关闭，但兼容开关仍可能被误开。

风险：两个 API 副本同时启动时可能并发建表/改列；发布过程中 API 重启会把迁移失败变成服务启动问题；误配置环境变量会重新引入重复调度。

建议：

1. API 启动只做连接和只读健康检查，不再执行 `create_all` 或业务迁移。
2. 迁移只允许由 `deploy_prod.sh` 或一次性 migration job 执行，并增加 migration history/版本锁。
3. 生产 API 镜像中移除 `API_START_SCHEDULER` 兼容路径，或在生产启动脚本中强制设置为 `false` 并启动即失败。

### P0-2：LiteLLM 动态配置路径不一致

证据：后端配置默认写入 [`backend/app/core/config.py`](../backend/app/core/config.py:58) 的 `/app/litellm_config.yaml`，同步代码使用该路径（[`backend/app/services/litellm_sync.py`](../backend/app/services/litellm_sync.py:52)）；但 Compose 中 LiteLLM 命令读取 `/app/config.yaml`，并将宿主机静态文件挂载到该路径（[`docker-compose.prod.yml`](../docker-compose.prod.yml:19-21)）。后端与 LiteLLM 当前不是同一个可写运行时文件。

风险：页面保存 GLM/其他 Provider 后，后端日志显示写入成功，但 LiteLLM 仍读取旧文件或空的 `model_list`；问题容易被误判为 API Key 或模型名称错误。

建议：使用一个专用共享卷，例如 `/runtime/litellm/config.yaml`，后端原子写入临时文件后 rename，LiteLLM 从同一文件读取；或明确让后端写入宿主机绑定文件并由 LiteLLM读取同一文件。完成后增加自动验收：配置更新 → 文件 hash 变化 → `/v1/models` 出现目标模型 → 实际请求成功。生产镜像必须固定版本或 digest，不要使用 `main-latest`。

### P0-3：备份“生成”和“恢复校验”不一致

证据：[`scripts/backup_db.sh`](../scripts/backup_db.sh:85-92) 已对多个数据库执行 `mysqldump --databases ... --source-data=2`，这是正确方向；但恢复校验先创建一个临时库，再导入包含原始数据库名的 dump（[`scripts/backup_db.sh`](../scripts/backup_db.sh:122-127)），随后却在临时库上下文中按原数据库名检查表（[`scripts/backup_db.sh`](../scripts/backup_db.sh:132-142)），逻辑不能证明三库都已恢复。另有用户数仍固定读取 `vllm_dashboard.users` 的兼容假设。回滚脚本 [`scripts/deploy_prod.sh`](../scripts/deploy_prod.sh:54-71) 也按单个 `DATABASE_NAME` drop/restore。

风险：`--verify-restore` 可能误报失败，也可能无法覆盖真正的三库恢复；跨 Schema 迁移后，升级失败的回滚不能保证恢复 Control、Collection、Telemetry 全部数据。

建议：恢复到隔离 MySQL 实例或为每个源库映射独立验证库，逐库校验 schema、关键表、行数和用户；回滚改为读取备份元数据中的数据库列表，禁止单库变量隐式决定恢复范围。恢复演练应包含 binlog 坐标和一次 PITR。

### P1-1：Compose 尚未具备 N 节点部署语义

证据：[`docker-compose.prod.yml`](../docker-compose.prod.yml:41-44、146-152、186-189、219-222) 仍使用 `build` 和固定 `container_name`；数据库连接仍写死为 `@mysql:3306`（49、193、226 行）；后端还挂载宿主机 Docker Socket（[`docker-compose.prod.yml`](../docker-compose.prod.yml:67-69)）。

风险：固定容器名阻止同一主机运行多个副本；每台节点现场 build 会产生不可复现镜像；服务名 `mysql` 无法平滑切换到文档要求的 `db.internal`；Docker Socket 相当于给 API 容器宿主机控制权限。

建议：生产 Compose 只使用不可变镜像 tag/digest；删除 `container_name`；数据库地址统一使用 `db.internal`；LiteLLM 重载改为受限运维 API 或独立 sidecar，移除 Docker Socket。节点加入/离开通过 inventory 和角色变量完成，而不是复制 Compose 文件后手工改名。

### P1-2：同步进度仍是进程内状态

证据：[`backend/app/services/sync_progress.py`](../backend/app/services/sync_progress.py:121) 使用全局 `_sync_progress` 保存进度。

风险：API 重启、容器漂移或多 API 副本时，用户看到的进度可能消失或因负载均衡命中不同副本而不一致。

建议：将 job、workflow、checkpoint、错误和心跳写入 MySQL 的持久化表；API 只读查询，Collector/Scheduler 通过事务更新。内存对象只能作为短期缓存，不能作为事实源。

### P1-3：文档与代码状态需要重新对齐

文档 v0.11 仍写着当前 `backup_db.sh` 没有三库和 `--source-data=2`（[`架构演进与运维方案.md`](架构演进与运维方案.md:283、353)），但代码已经加入这些能力。反过来，文档中的 `db.internal`、固定镜像、共享运行时配置等目标，在 Compose 中尚未实现。

建议：把每个 Step 的状态统一为“已实现 / 部分实现 / 仅设计 / 阻断条件”，并在每项后面绑定代码路径和验收命令，避免只靠自然语言描述当前状态。

## 5. 建议实施顺序

1. 先修正备份恢复校验和三库回滚，完成一次隔离恢复、一次 binlog/PITR 演练。
2. 再移除 API 启动迁移和 Scheduler 兼容路径，增加 migration job 与迁移版本锁。
3. 修正 LiteLLM 共享运行时配置，固定镜像版本，增加配置更新后的端到端测试。
4. 将 Compose 改为不可变镜像、无固定容器名、`db.internal`、无 Docker Socket；单机先验证，再复制到第二台 Linux/Windows-VM 节点。
5. 最后再启用第二 Collector、第一/第二 Replica、DNS 切换和故障演练。没有通过前四步验收时，不要进行跨 Schema 正式迁移。

## 6. 发布前必须通过的验收清单

- [ ] 两个 API 副本同时启动，不执行 DDL、不启动 Scheduler，且健康检查均通过。
- [ ] migration job 可重复执行，具有版本记录和并发锁。
- [ ] Provider 配置更新后，LiteLLM 实际读取的文件 hash 变化，模型可在 `/v1/models` 查询并完成真实请求。
- [ ] 备份包含所有实际存在的业务库、binlog 坐标和 SHA-256；隔离恢复后关键表/行数校验通过。
- [ ] 回滚可恢复所有业务库，而不是只恢复 `${MYSQL_DATABASE}`。
- [ ] Collector 被强制终止后，另一实例可在租约过期后接管；旧实例的 checkpoint/complete 操作被 fencing 拒绝。
- [ ] Compose 配置不含 `container_name`、现场 `build`、宿主机 Docker Socket 或 `@mysql` 硬编码。
- [ ] 至少完成一次单机故障、磁盘满、数据库不可达和 LiteLLM 不可用演练，并记录 RTO/RPO。

## 7. 最终判断

这份方案作为演进蓝图是合理的，尤其是“计算可抛弃、数据和配置外置、逐阶段扩容”的核心思想没有问题。当前最需要改进的不是再增加更多组件，而是把已经写进文档的边界落实到启动入口、备份恢复、配置共享和镜像发布这四个可验证的工程契约上。完成这些修复后，才适合把第二台及更多 Linux/Windows 设备接入同一套部署模型。
