# 项目代码与架构全面审查报告

> 审查日期：2026-08-10  
> 审查范围：本地开发、测试、生产 Compose、部署脚本、Docker 镜像、数据库迁移、配置/密钥、CI 和项目文档。  
> 审查方式：静态检查仓库文件；未连接生产环境，未执行删除、升级或数据库变更。

## 1. 总体判断

项目不是“某一个模块有问题”，而是**多个阶段的实现同时存在**：早期单机脚本、Docker Desktop 本地开发、当前生产 Compose、Phase A 服务拆分和未来多节点设计并存。每一套都能解释局部行为，但它们没有由一个统一的开发/发布契约串起来，因此容易出现“本地能跑、生产能跑，但升级和扩容不可预测”的情况。

当前建议评级：

| 领域 | 评级 | 结论 |
|---|---|---|
| 业务功能 | B | 功能较完整，后端服务和前端页面数量较多 |
| 本地开发一致性 | C- | PowerShell、Shell、Desktop Compose、直接 `uvicorn` 互相不完全兼容 |
| 生产发布安全 | C | 有备份/回滚框架，但仍有旧脚本可绕过安全流程 |
| 数据库演进 | C- | 多套迁移入口并存，API 仍在启动时 DDL |
| 可扩展性 | C | 设计方向正确，Compose 和运行时绑定仍是单机模式 |
| 可复现构建 | D+ | 后端无锁定依赖，多个基础镜像和 LiteLLM 使用可变 tag |
| 安全基线 | C- | 存在弱默认口令、Docker Socket、宽松 CORS/CSP 等问题 |

最重要的判断是：**先收敛运行方式，再继续做业务和多节点扩容**。继续增加功能会进一步放大现有的配置漂移和发布风险。

## 2. 问题分级

### P0：应立即处理

1. 生产升级存在两套入口，旧入口可绕过备份验证和回滚。
2. 数据库迁移有四类入口：API lifespan、`init_db.py`、多个 `upgrade_v*.py`、新迁移脚本。
3. 本地/生产环境的数据库地址、服务名和 LiteLLM 依赖不一致，导致“环境能启动但连错服务”。
4. 后端容器通过 Docker Socket 控制宿主机，权限边界过大。

### P1：应在下一阶段处理

1. 后端依赖和镜像不可复现，存在 `latest`、范围版本和无 `uv.lock`。
2. 进度、缓存、Git 仓库和报告文件的持久化边界没有统一定义。
3. CI 只构建并推送镜像，不运行后端/前端测试、迁移测试或安全扫描。
4. Nginx 配置存在重复加载风险，并且 CORS/CSP 过于宽松。
5. 开发启动脚本会写入弱 JWT、默认管理员密码，并且两套脚本行为不同。

### P2：技术债

1. `backend/scripts` 中有大量历史升级脚本、预览脚本和一次性工具，缺少生命周期标记。
2. 文档、脚本和实际 Compose 的命名与状态经常不一致。
3. 根目录存在大量日志、文档、截图和分析产物，项目边界不清晰。

## 3. 关键发现

### 3.1 生产发布路径有两个“真相源”

当前至少有：

- [`deploy.sh`](../deploy.sh)：旧的通用 Compose 控制脚本；`start/rebuild/upgrade` 会直接 `up -d --build`，并在部署后执行 `init_db.py`（[`deploy.sh`](../deploy.sh:189-213)）。其备份只导出单个 `vllm_dashboard`（[`deploy.sh`](../deploy.sh:307-330)）。
- [`scripts/deploy_prod.sh`](../scripts/deploy_prod.sh:96-176)：新的安全发布脚本，包含备份恢复验证、显式迁移、健康检查和回滚。

风险是运维人员按 README/QUICKSTART 使用旧命令，就会绕过新流程。两个脚本还使用不同的容器名、备份位置、恢复逻辑和迁移入口。

建议：

1. 只保留一个生产入口：`scripts/deploy_prod.sh`。
2. `deploy.sh` 改名为 `dev-compose.sh` 或仅保留本地开发命令；禁止它操作生产环境。
3. README、QUICKSTART、生产升级指南统一只引用一个入口，并在脚本开头校验 `ENVIRONMENT=production` 和目标环境。

### 3.2 数据库迁移职责没有收敛

当前存在以下迁移方式：

- API 启动时 `Base.metadata.create_all` 和列级 `ALTER TABLE`（[`backend/app/main.py`](../backend/app/main.py:71-84、428)）。
- [`backend/scripts/init_db.py`](../backend/scripts/init_db.py:161) 再次使用 `create_all`，并包含大量历史列变更。
- 约 34 个 `upgrade_v*.py` 历史脚本。
- [`backend/scripts/migrate_mysql_schema.py`](../backend/scripts/migrate_mysql_schema.py) 和 [`migrate_phase_a.py`](../backend/scripts/migrate_phase_a.py)。

这不是单纯的“脚本多”，而是缺少唯一迁移顺序和版本状态。新环境、旧环境、测试环境可能走不同路径，最终得到不同 schema。

建议：

- 选择 Alembic 或现有 `schema_migrations` 机制作为唯一事实源，不要两者并用。
- API 和 Scheduler 进程禁止执行 DDL。
- 历史脚本按版本冻结；只允许一个迁移命令推进版本。
- CI 建立“空库升级”和“当前生产备份升级”两条测试链，并检查迁移幂等性。

### 3.3 本地开发有四种启动方式，彼此不等价

现有方式包括：

1. `uv run uvicorn` 直接启动后端。
2. `dev-setup.ps1`：手动 `docker run` 后端，可选手动 LiteLLM。
3. `dev-setup.sh`：另一套手动 `docker run`，行为和 PowerShell 版本不同。
4. `docker-compose.desktop.yml`：要求外部网络 `vllm-dev-net`、外部卷和一个预先存在的 `mysql-replica` 服务。

具体不一致包括：

- PowerShell 脚本创建/使用的数据库端口是 `127.0.0.1:3308`，Desktop Compose 使用容器内 `mysql-replica:3306`。
- Desktop Compose 的 `vllm-dev-net` 和 `vllm_backend_data` 声明为 external，但仓库没有完整的创建和初始化步骤。
- 两个 setup 脚本都使用弱的本地 JWT 和 `admin/admin123`。
- Shell 版本默认不启动 LiteLLM，PowerShell 版本有交互式 LiteLLM 分支。

建议只保留一个开发编排：推荐 `docker-compose.dev.yml`，提供 MySQL、LiteLLM、backend、frontend 四个服务；Windows/Linux 只通过 `.env.local` 改端口和挂载路径，不再手写 `docker run`。

### 3.4 Compose 仍然把生产服务绑定在单机

[`docker-compose.prod.yml`](../docker-compose.prod.yml) 仍存在：

- backend/frontend/scheduler/collector 使用 `build`（41、146、186、219 行）；
- 固定 `container_name`（44、152、189、222 行）；
- 数据库地址写死为 Compose 服务名 `mysql`（49、193、226 行）；
- backend 挂载 `/var/run/docker.sock`（67-69 行）。

这与目标中的“不可变镜像、`db.internal`、可复制节点”不一致。当前 Compose 可以作为单机过渡，但不能直接作为多节点部署模板。

建议：生产只使用 CI 发布的不可变镜像 tag/digest；删除 `container_name`；统一通过 `db.internal` 访问 MySQL；LiteLLM 重载使用受限 API/sidecar，移除 Docker Socket。

### 3.5 LiteLLM 的配置边界同时有静态文件、数据库和 Docker 控制

后端同步服务从数据库生成配置文件并尝试重启 LiteLLM，但 Compose 中 LiteLLM 读取 `/app/config.yaml`，后端默认写 `/app/litellm_config.yaml`。这造成配置事实源不明确。

此外，[`backend/app/services/litellm_sync.py`](../backend/app/services/litellm_sync.py:161-169) 会尝试访问 Docker Socket；生产 Compose 也直接挂载该 Socket。即使功能可用，后端 API 也拥有控制同一宿主机其他容器的能力。

建议明确唯一模型配置链：数据库 → 受控配置渲染器 → 共享运行时文件/配置服务 → LiteLLM reload。API 不应直接管理 Docker daemon。

### 3.6 构建不可复现

后端 [`pyproject.toml`](../backend/pyproject.toml) 使用大量 `>=` 版本范围，仓库没有 `uv.lock`（且 `.gitignore` 明确忽略它）；[`backend/Dockerfile.prod`](../backend/Dockerfile.prod) 使用 `uv:latest` 和多个滚动基础镜像；生产 LiteLLM 使用 `ghcr.io/berriai/litellm:main-latest`。

风险：同一 commit 在不同日期构建出不同依赖，升级后出现难以回滚的行为变化。

建议：提交 `uv.lock`，锁定 Python/Node/系统包和镜像 digest；CI 只发布带 commit/version 的镜像，`latest` 仅作开发便利标签。

### 3.7 CI/CD 只负责“构建并推送”

`.github/workflows/build-and-push.yml` 当前主要完成 checkout、登录 GHCR、Buildx 和两张镜像推送，没有：

- 后端 pytest/ruff/mypy；
- 前端 lint/test/build 验证；
- 数据库空库迁移和备份恢复测试；
- 镜像漏洞扫描、SBOM、签名或 digest 输出；
- 生产部署前的配置校验。

建议拆成 `quality.yml`、`image.yml`、`deploy.yml` 三阶段，并将镜像 digest 作为部署输入，而不是默认推送并使用 `latest`。

### 3.8 Nginx 配置可能重复加载且安全策略过宽

前端镜像已经把 `nginx.conf` 复制为 `/etc/nginx/conf.d/default.conf`，生产 Compose 又把同一配置挂载为 `custom.conf`（[`docker-compose.prod.yml`](../docker-compose.prod.yml:155-157)）。若两份都含 `server { listen 80; }`，可能产生重复 server/默认路由行为。

[`deploy/config/nginx.conf`](../deploy/config/nginx.conf) 还配置了 `Access-Control-Allow-Origin *`、`connect-src *`、`unsafe-inline` 和 `unsafe-eval`。对于带 JWT 和管理接口的系统，这扩大了浏览器攻击面。

建议：镜像内置配置和运行时挂载二选一；限制允许来源为实际域名；按需删除 `unsafe-eval`，并把 API 与前端的 CORS 责任统一到一层。

### 3.9 持久化边界不清楚

Compose 将 `backend_data` 用于 Git 缓存、报告和其他运行时数据，同时 scheduler/collector 共享该卷；MySQL 使用 `mysql_data`；LiteLLM 依赖宿主机配置文件。文档虽然提出“数据源、配置、数据外置”，但代码没有清晰区分：

- 必须备份的业务数据；
- 可以删除后重建的缓存；
- 只能由单个 worker 写入的临时目录；
- 需要对象存储/异地备份的报告附件。

建议建立数据分类表和卷清单，每个目录标注 owner、是否可重建、备份频率、恢复方式和跨节点共享要求。

### 3.10 安全和仓库卫生问题

- `dev-setup.ps1`/`dev-setup.sh` 写入弱 JWT 和默认管理员密码；必须明确仅限本地，并避免把凭据打印到终端历史。
- `.gitignore` 中包含乱码路径规则，导致正式架构文档被忽略；`git ls-files` 未发现该文档被版本控制。重要设计文档无法随代码审查和发布追踪。
- 根目录存在大量日志、覆盖率、截图、Office 文档和临时分析文件。虽然多数被忽略，但会干扰开发者判断项目边界。
- `deploy/config/litellm_runtime.yaml` 被设计为生成文件，可能含明文 API Key；应确保只存在于受限运行目录，并在启动时校验权限。

## 4. 建议的目标仓库结构

```text
/
├─ apps/
│  ├─ api/                 # 只提供 API/Query，不做迁移、不启动 Scheduler
│  ├─ scheduler/           # 调度和 leader lease
│  └─ collector/           # Python/C++ worker
├─ frontend/
├─ db/
│  ├─ migrations/          # 唯一迁移目录
│  └─ seeds/
├─ deploy/
│  ├─ compose/dev.yml
│  ├─ compose/prod.yml
│  ├─ env/*.example
│  └─ config/
├─ ops/
│  ├─ backup/
│  ├─ restore/
│  ├─ health/
│  └─ release/
├─ scripts/
│  └─ dev.sh / release.sh  # 只保留薄封装
└─ docs/
```

短期不必真的重排所有目录，但应先建立“逻辑边界”：`dev`、`test`、`release` 三套命令分别负责什么，任何命令不能跨边界偷偷做另一套事情。

## 5. 推荐整改顺序

### 阶段 1：收敛入口（1～2 天）

- 宣布 `scripts/deploy_prod.sh` 为唯一生产发布入口。
- 将 `deploy.sh` 限定为本地开发，移除生产升级和危险的 `down -v` 示例。
- 补充 `make`/PowerShell 等价命令，但底层都调用同一套 Compose 文件。

### 阶段 2：收敛数据库（3～5 天）

- API/Scheduler 禁止启动 DDL。
- 选择唯一迁移框架，归档 34 个历史脚本。
- 增加空库、旧库、重复执行和备份恢复测试。

### 阶段 3：收敛配置和构建（2～4 天）

- 修复 LiteLLM 共享配置路径。
- 提交 `uv.lock`，固定基础镜像和 LiteLLM digest。
- 把本地配置、生产配置、运行时秘密分为 `.env.example`、`.env.local`、Secret Store 三类。

### 阶段 4：建立 CI 门禁（2～4 天）

- PR 必须通过后端测试/ruff、前端 lint/test/build、迁移测试。
- 镜像发布增加漏洞扫描、SBOM 和 digest 产物。
- 部署脚本只接受明确版本，不接受 `latest`。

### 阶段 5：再做多节点（通过前四阶段后）

- Compose 使用不可变镜像和 `db.internal`。
- 先增加第二 Collector，再验证 API 多副本。
- 最后才做 MySQL Replica、DNS 切换和故障演练。

## 7. 最终结论

项目的业务代码量和功能已经达到需要“工程化治理”的规模。当前最大的风险不是技术选型，而是**同一项目存在多套运行方式和多套发布真相**。建议暂停继续堆叠新功能，先完成入口、迁移、配置、构建和 CI 五项收敛。完成后，现有的 MySQL、Scheduler/Collector 拆分和“计算可抛弃”架构才会真正变成可维护、可升级、可扩展的基础设施。

## 8. 代码与目录结构专项审查

### 8.1 规模已经超过“单文件快速迭代”阶段

静态统计结果：`backend/app` 约 111 个 Python 文件，`frontend/src` 约 117 个 TypeScript/TSX 文件，后端路由 21 个，服务模块超过 50 个。多个文件已经达到 1,000～3,000 行：

| 文件 | 规模 | 主要问题 |
|---|---:|---|
| `frontend/src/pages/SystemConfig.tsx` | 约 2,930 行 | 页面、表单、权限、同步操作和配置状态混在一起 |
| `frontend/src/pages/ModelBoardConfig.tsx` | 约 2,695 行 | 配置编辑、同步、展示和错误处理耦合 |
| `backend/app/services/failure_analysis.py` | 约 2,077 行 | LLM 配置、上下文构建、任务状态、PDF/文件和持久化混合 |
| `backend/app/api/v1/ci.py` | 约 1,790 行 | 路由、后台任务、采集、状态和统计集中在一个模块 |
| `backend/app/services/scheduler.py` | 约 1,496 行 | 调度、同步策略、数据库访问和业务规则混合 |
| `backend/app/models/__init__.py` | 约 848 行 | 大量领域模型集中在一个文件 |
| `backend/app/schemas/__init__.py` | 约 1,096 行 | 所有 API schema 集中，边界难以维护 |

这会带来三个实际后果：修改一个功能容易触碰其他功能；测试只能通过大范围 fixture 建立上下文；多人协作时冲突集中在少数大文件。

建议按领域拆分，而不是按“文件类型”继续堆积：

```text
backend/app/domains/
├─ auth/
├─ ci/
│  ├─ api.py
│  ├─ service.py
│  ├─ repository.py
│  ├─ models.py
│  └─ schemas.py
├─ reports/
├─ issue_analysis/
├─ model_registry/
└─ resources/
```

每个领域内部再分 API、应用服务、repository、模型和 schema；跨领域只通过应用服务接口调用，不直接访问另一个领域的表。

### 8.2 API 层和 Service 层没有真正隔离

大量 API 文件直接执行 `db.commit()`、构造 `SessionLocal`、启动后台任务和调用外部 GitHub/CLI。典型位置包括 `ci.py`、`test_board.py`、`system_config.py`、`pr_pipeline.py`。

这使 API 层同时承担：HTTP 参数校验、权限、事务边界、任务调度、外部 IO 和业务规则。结果是无法把同一业务安全地迁移到 Scheduler/Collector，也很难对服务做纯单元测试。

建议固定调用链：

```text
Router → Application Service → Repository/Adapter → MySQL/外部系统
```

Router 不直接 `commit()`，Service 决定事务边界，Repository 负责查询，GitHub/CLI/Kubernetes 通过 adapter 注入。

### 8.3 请求内 `asyncio.create_task()` 不是可靠任务系统

代码中存在多个请求触发的进程内后台任务，例如：

- `backend/app/api/v1/ci.py:462` 启动 CI 同步；
- `backend/app/api/v1/ci.py:1077` 启动失败分析；
- `backend/app/api/v1/pr_pipeline.py:151` 启动 PR 同步；
- `backend/app/services/coverage_sync.py` 和 `failure_analysis.py` 也创建后台任务。

这些任务在进程重启、容器替换、部署滚动更新或多 API 副本时没有可靠恢复语义。`pr_pipeline.py` 的 `_sync_running` 还是进程内布尔值，多副本时每个副本都可能认为自己没有任务在运行。

建议所有长任务统一写入 `collection_tasks`/业务 job 表，由 Scheduler 创建、Collector 领取；API 只提交任务并返回 job id。这样才能使用既定的 lease、checkpoint、fencing 和重试模型。

### 8.4 进程内缓存与文件缓存没有统一抽象

当前代码同时使用：进程全局变量、`DATA_DIR` 文件、Git 仓库缓存、数据库 JSON 字段、后台日志文件和 Docker volume。比如同步进度在 `sync_progress.py` 里是全局对象，而 GitHub cache、失败分析和报告又各自实现文件存储。

建议建立统一的 Storage Contract：

| 类型 | 事实源 | 是否可丢弃 | 访问方式 |
|---|---|---|---|
| 任务状态/租约/进度 | MySQL | 否 | Repository/事务 |
| GitHub/Git 仓库缓存 | 本地卷或对象存储 | 是 | Cache adapter |
| 报告正文/附件 | 对象存储或版本化卷 | 否 | FileStore adapter |
| 日志 | stdout + 日志系统 | 通常可重建 | logging adapter |
| LiteLLM 运行配置 | 受控运行目录 | 可重建但需保留版本 | Config renderer |

### 8.5 外部命令执行需要单独的安全边界

`agent_tools.py` 的 `run_bash` 使用 `subprocess.run(..., shell=True)`，仅靠字符串黑名单阻止少数命令。黑名单不能可靠阻止 shell 语法、命令替换、重定向变体或间接调用；该工具还被 Agent 能力使用。

建议：

- 默认只允许结构化命令白名单，使用 `shell=False`。
- 必须执行 shell 时，将 Agent 放入独立、无生产凭据、只读工作目录的沙箱容器。
- 将 Git、文件读取、测试执行拆成独立工具，不提供通用 bash。
- 对命令、操作者、仓库、耗时和输出做审计记录。

### 8.6 数据库连接池和运行配置存在漂移

`backend/app/db/base.py` 实际设置 `pool_size=20`、`max_overflow=20`，但日志仍写“pool_size=5, max_overflow=10”。在 2GB 内存生产机上，如果 API、Scheduler、Collector 各自建立连接池，理论连接数可能迅速达到上百。

建议：按角色配置连接池上限，明确公式并监控 `Threads_connected`；低内存单机默认降低池大小，扩容时再提升。日志必须输出真实配置，避免排障误判。

### 8.7 前端页面和 API 文件需要按功能拆分

前端多个页面超过 1,000 行，后端多个路由超过 1,000 行；这通常意味着页面组件、数据请求、表单 schema、表格列和业务状态没有拆开。

建议每个页面只保留布局和组合逻辑，抽出：

- `features/<domain>/api.ts`：接口调用；
- `features/<domain>/queries.ts`：React Query hooks；
- `features/<domain>/schemas.ts`：表单/响应类型；
- `features/<domain>/components/`：表格、弹窗、图表；
- `features/<domain>/pages/`：页面编排。

同时把前端硬编码的 `/api/v1/...` 路径集中到 API client，避免 `axios`、`fetch`、直接 `window.location` 三种调用方式并存。

### 8.8 目录中混入了运行产物和一次性工具

根目录和 backend 下存在大量日志、预览 HTML、截图、Office 文档、分析结果和一次性脚本。多数被 `.gitignore` 忽略，但它们仍会影响本地搜索、镜像构建上下文和开发者理解项目结构。

建议把本地产物全部移到 `.local/` 或系统临时目录；把一次性工具迁移到 `tools/` 并标注“不可用于生产”；Docker build context 中显式排除测试产物、日志、报告和缓存。

## 9. 代码专项整改优先级

1. **先改可靠性**：移除请求内后台任务，统一写任务表；API/Scheduler 禁止 DDL。
2. **再改边界**：按领域拆分超大路由/服务文件，建立 repository 和 adapter 层。
3. **再改安全**：移除通用 `run_bash`、Docker Socket 和弱默认密码。
4. **再改可维护性**：拆分模型/schema 大文件，清理一次性脚本和运行产物。
5. **最后优化性能**：根据角色重新设定连接池、缓存和 worker 并发，不要在边界未稳定前盲目增加并发。
